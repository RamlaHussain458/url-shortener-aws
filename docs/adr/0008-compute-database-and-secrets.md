# 0008. Compute, database and secrets choices

**Status:** Accepted

**Context:** The application needs a server for two containers (API and web), a MySQL database, a place to store images, and a safe way to hold the database password. The account runs on limited credits, so every hour of running resources matters.

**Decision:**
- One EC2 instance (`t3.small`, x86, Amazon Linux 2023) runs Docker. x86 matches the images built on a normal PC and in GitHub Actions. IMDSv2 is required and the disk is encrypted.
- The database is RDS MySQL 8.4 on `db.t4g.micro`, single availability zone, in the private subnets, encrypted, not publicly accessible.
- Images live in two private ECR repositories with immutable tags, scan on push, and a lifecycle policy that keeps only the latest few images.
- The server uses an IAM role (no access keys) that allows Session Manager, pulling the two images, and reading this project's parameters.
- The database password is generated by Terraform and stored as a SecureString in Systems Manager Parameter Store, which is free. Secrets Manager would cost money per secret.
- A fixed Elastic IP gives the server a stable public address.

**Consequences:**
- There is no SSH. Shell access uses Session Manager.
- The Terraform state contains the generated password, so the state bucket must stay private, encrypted and versioned (see ADR 0006).
- The application connects as the database's main user. A dedicated limited user would be a sensible later improvement.
- The server, the database and the public IP address cost money every hour. They are removed with a targeted `terraform destroy` between work sessions.
- A single availability zone and no automatic failover mean the database is not highly available. That is acceptable for a demo and would change in production.
